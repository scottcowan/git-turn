# Phase 03.1 Plan 01: Turn Heatmap Core Logic Summary

**Pure calendar-day bucketing, data-relative density levels, activity summary stats, and a bounded Sunday-first week-column grid model for `git turn heatmap`, built and unit tested (23 tests) with zero git dependency.**

## Performance

- **Duration:** 35 min

- **Completed:** 2026-09-07T15:52:34Z
- **Tasks:** 3
- **Files modified:** 2 (both created)

## Accomplishments
- `dayKey()` buckets turns by LOCAL calendar day (never UTC-slicing), proven by a TZ-independent 23:30-local test that crosses the UTC date line
- `groupByCalendarDay()` merges turns from every session into one bucket per day (D-02 cross-session scope)
- `bucketFor()` derives 0..4 density levels relative to the caller's own max-per-day, proven identical at both a 4-count and a 200-count data scale (D-01)
- `computeSummaryStats()` derives totals, active days, busiest day (earliest-date tie-break), first/last day, and DST-safe streak counts from day buckets alone, with no token/cost/model data (D-04)
- `availableWeeks()` and `buildWeekColumns()` produce a bounded (max 53 weeks), terminal-width-aware, endDate-anchored grid — resolving research Open Question 1 in a code comment (D-03)

## Decisions Made
- Followed the plan's `<interface_contract>` verbatim — no renamed/reshaped exports, since Plan 02 consumes them directly.
- `computeSummaryStats` sorts day keys lexicographically (safe for `YYYY-MM-DD`) rather than parsing to `Date` for ordering, avoiding needless Date object churn on the hot aggregation path.
- Streak arithmetic uses `new Date(y, m0, d+1)` component stepping exclusively — confirmed via `grep -c '86400000'` returning 0 — to stay DST-safe per the plan's explicit instruction.
