## Summary

This phase adds a new zero-dependency command, `git turn heatmap`, that renders a GitHub-contribution-style calendar grid in the terminal using raw ANSI escape codes, colored by daily turn-count density across all sessions. All the enumeration and color-gating infrastructure this command needs already exists and should be reused, not reinvented: `listAllTurns({ noCache })` in `src/blame-util.js` gives cache-first/ref-walk-fallback cross-session turn data with a confirmed ISO-8601 `ts` field, and `shouldColor()` in `src/git.js` gives the exact NO_COLOR/FORCE_COLOR/TTY gating convention already used by `diff.js` and `show.js`. Nothing in the existing codebase groups turns by calendar day — this phase must build that aggregation fresh (it does not exist in `cost.js`, `log.js`, or anywhere else).

The rendering approach itself has no npm dependency to lean on (project convention forbids new dependencies), so the grid must be hand-built from raw ANSI SGR background-color escapes (`\x1b[48;5;{n}m` 256-color or `\x1b[48;2;{r};{g};{b}m` truecolor) applied to whitespace/block-character cells, reset with `\x1b[0m`. This is a well-established terminal pattern (used by real GitHub-heatmap CLI clones) and requires no external library — just careful column/row layout math and a discrete color-bucket function.

**Primary recommendation:** Build `src/commands/heatmap.js` following the exact module shape (`module.exports = { run(args) }`) and cache-first-via-`listAllTurns` pattern used by `blame.js`/`bisect.js`. Group turns into a `Map<'YYYY-MM-DD', count>` keyed off the date portion of each turn's ISO `ts` field (local time, not UTC-sliced — see Pitfall 1). Render columns as ISO weeks (Monday-start, matching git-log conventions elsewhere in the codebase is not required since there's no existing day-of-week convention to match) with 5 discrete color buckets (0 turns = dim gray, then 4 intensity steps) gated by `shouldColor()`, falling back to a plain-text density-character legend (` `, `.`, `:`, `+`, `#` or similar) when color is disabled. Compute terminal width via `process.stdout.columns` and truncate to the most recent N weeks that fit rather than wrapping, since no existing command in this codebase does width-aware truncation (this is new ground) — document this explicitly as new precedent in the plan.

**What:** Bucket turns by the local calendar date derived from each turn's ISO-8601 `ts` field.

**Example:**

```javascript
// NEW code for this phase — ts confirmed as new Date().toISOString()
// (src/hooks/post-commit.js:25, :88 — e.g. "2026-09-07T12:30:00.000Z")
function dayKey(isoTs) {
  const d = new Date(isoTs);
  // Use LOCAL date components, not the raw UTC-prefix slice — see Pitfall 1.
  const y = d.getFullYear();
  const m = String(d.getMonth() + 1).padStart(2, '0');
  const day = String(d.getDate()).padStart(2, '0');
  return `${y}-${m}-${day}`;
}

function groupByCalendarDay(turns) {
  const map = new Map();
  for (const t of turns) {
    const key = dayKey(t.ts);
    map.set(key, (map.get(key) || 0) + 1);
  }
  return map;
}
```

### ANSI Calendar-Heatmap Rendering Approach (investigated per instruction #1)

There is no npm dependency to inspect (project forbids adding one), so this is a from-first-principles design based on how GitHub-style terminal contribution graphs are conventionally built (verified against general ANSI SGR spec knowledge — `[ASSUMED]`, standard and stable, not project-specific):

- **Layout:** Columns = weeks (Monday-first or Sunday-first, discretion — recommend Sunday-first to match GitHub's own convention, which the reference screenshots were modeled on), rows = 7 day-of-week slots. Each cell is 2 characters wide (a colored double-space or two block glyphs) to render roughly square in most monospace terminal fonts.
- **Month labels:** A single header row printed above the grid, with month abbreviations placed above the column where that month's first week starts. Requires tracking which week-column index corresponds to each month transition.
- **Day-of-week labels:** A single-character or 3-letter column to the left of the grid (e.g. `Mon`, `Wed`, `Fri` printed, other rows blank) — matches the reference screenshot description in the todo file.
- **Color steps:** 5 buckets total (0 turns = neutral/dim, then 4 intensity levels for >0) is the simplest mapping of the reference's "4-step Less → More" legend plus a zero state. Bucket boundaries should be computed from the actual data's max-per-day (e.g. quartiles of nonzero days), not fixed absolute thresholds — a repo with max 3 turns/day and a repo with max 200 turns/day need different bucket cutoffs to be visually meaningful. `[ASSUMED — standard heatmap practice, ​not verified against a specific reference implementation since none is in the dependency tree]`.
- **ANSI codes:** 256-color mode (`\x1b[48;5;{0-255}m`) is safer than truecolor (`\x1b[48;2;r;g;bm`) for broad terminal compatibility — truecolor requires COLORTERM=truecolor or a modern terminal; 256-color has near-universal support in 2020s+ terminals. Recommend 256-color palette (e.g. green ramp: 22, 28, 34, 40, 46 or similar) with a fallback ASCII-glyph legend when `shouldColor()` is false.
- **Reset:** Every colored cell MUST end with `\x1b[0m` to avoid color bleed into subsequent output — this is the single most common ANSI-rendering bug in hand-rolled terminal graphics.

### Anti-Patterns to Avoid
- **Slicing the ISO string for date grouping (`ts.slice(0, 10)`):** This takes the UTC calendar date, not the user's local calendar date. A turn made at 23:30 local time that crossed midnight UTC would land on the wrong day in the grid. Use `new Date(ts)` and local getters (`getFullYear`/`getMonth`/`getDate`), not string slicing or `getUTCDate()`. See Pitfall 1 below.
- **Emitting raw truecolor escapes without a `shouldColor()` gate:** Breaks NO_COLOR compliance and pollutes piped output (e.g. `git turn heatmap | grep ...`) with escape garbage.
- **Wrapping the grid across multiple lines when it doesn't fit terminal width:** Produces a visually broken calendar (columns misaligned across wrapped lines). Truncating to "most recent N weeks that fit" is far more usable than wrapping.

## Common Pitfalls

### Pitfall 1: UTC vs. local calendar-day slicing
**What goes wrong:** Grouping turns by day using `ts.slice(0, 10)` (a raw UTC-date substring of the ISO string) silently assigns turns to the wrong day for any user not in UTC, especially near midnight.
**Why it happens:** ISO-8601 `toISOString()` output is always UTC; slicing the first 10 characters looks like "the date" but is a UTC date, not the machine's local date.
**How to avoid:** Parse with `new Date(ts)` and use local getters (`getFullYear()`, `getMonth()`, `getDate()`) when building the day key.
**Warning signs:** Turns near 00:00 local time cluster on the "wrong side" of a day boundary in manual testing; date totals shift by exactly the UTC-offset hours when compared against `git log --date=local`.

### Pitfall 2: Fixed color-bucket thresholds regardless of data scale
**What goes wrong:** A hardcoded "1-2 turns = light, 3-5 = medium, 6-10 = dark, 11+ = darkest" scale looks empty (all light) on a low-activity repo and looks maxed-out (all darkest) on a high-activity repo.
**Why it happens:** Copying the reference screenshot's exact numeric buckets without checking that they were tuned to that screenshot's specific (unknown) dataset.
**How to avoid:** Compute bucket boundaries from the actual max/distribution of the current repo's day-counts (e.g. simple max/4 quantiles, or a log scale for skewed data) rather than fixed absolute counts.
**Warning signs:** Manual test with a repo that has 1 active day vs. a repo with 200 active days — if the grid looks identical (all one color) in both, thresholds are broken.

### Pitfall 3: ANSI color bleed from missing reset codes
**What goes wrong:** Terminal background color persists past the intended cell, coloring subsequent text (stat block, next line) unexpectedly.
**Why it happens:** Forgetting `\x1b[0m` after each colored segment, or resetting only at end-of-line instead of end-of-cell when cells are concatenated with plain-text labels between them.
**How to avoid:** Wrap every individually-colored cell in its own open/reset pair rather than relying on a single trailing reset for the whole line.
**Warning signs:** Running the command and seeing colored background extend into the day-of-week labels or the summary stats below the grid.

### Pitfall 4: Assuming a fixed terminal width
**What goes wrong:** A hardcoded 106-column grid (52-53 weeks × 2 chars) renders wrapped/broken in terminals narrower than that (common: 80-column default, split panes, narrow SSH sessions).
**Why it happens:** No existing command in this codebase does width-aware rendering, so there's no established pattern to copy — this is genuinely new ground for the project.
**How to avoid:** Read `process.stdout.columns` (undefined when not a TTY — default to a safe assumption like 80 or the full year, since piped output doesn't have a "wrap" problem the same way) and truncate to the most recent N weeks that fit, rather than emitting the full year unconditionally.
**Warning signs:** Testing in a resized/narrow terminal window shows the grid's right edge wrapping to a new line, breaking column alignment.

## Code Examples

### Terminal width detection (new precedent for this project)
```javascript
// No existing command does this — new pattern for heatmap.js.
// process.stdout.columns is undefined when stdout is not a TTY (e.g. piped to a file).
function getAvailableWeeks() {
  const cols = process.stdout.columns;
  if (!cols) return 53; // full year, safe default for non-TTY (piped/redirected) output
  const labelWidth = 4; // day-of-week label column
  const cellWidth = 2;
  return Math.max(1, Math.floor((cols - labelWidth) / cellWidth));
}
```

### Grouping and stats (new — no existing helper to cite)
```javascript
function computeSummaryStats(dayMap) {
  const entries = [...dayMap.entries()];
  if (entries.length === 0) return { activeDays: 0, totalTurns: 0, busiestDay: null, busiestCount: 0 };
  const totalTurns = entries.reduce((sum, [, count]) => sum + count, 0);
  const [busiestDay, busiestCount] = entries.reduce((max, e) => e[1] > max[1] ? e : max, entries[0]);
  return { activeDays: entries.length, totalTurns, busiestDay, busiestCount };
}
```
