## Warnings

### WR-01: `maxCount` is computed from the entire (unbounded) history, not the rendered window, contradicting the code's own documented guarantee

**File:** `src/commands/heatmap.js:320` (`run()`), with the guarantee stated in the header comment at lines 9-10 and the `bucketFor` comment at lines 39-42.

**Issue:** The module header states: "Density levels are deliberately data-relative — computed from the caller's own max-per-day... so a low-activity repo and a high-activity repo both render the full 0..4 level range." `bucketFor`'s own comment repeats: "the top of the caller's own data range always reaches level 4." However, `run()` computes `maxCount` from `dayMap` (the *entire* all-time turn history) while the grid rendered to the user is a bounded window of at most `MAX_WEEKS` (53) weeks / `availableWeeks()` columns (`buildWeekColumns`, `heatmap.js:148-178`). If the single busiest day in the repo's history falls outside the rendered window (e.g. a burst of activity 2 years ago in a repo now rendering only the last 38 weeks), no cell in the *visible* grid will ever reach level 4 — every visible cell is scaled against an off-screen maximum the user cannot see. This directly contradicts the stated guarantee that "a low-activity repo and a high-activity repo both render the full 0..4 level range," which only holds when the busiest day happens to fall inside the window.

**Fix:** Compute `maxCount` from the counts actually present in `grid` (the rendered window), not from the full `dayMap`:
```javascript
const maxCount = Math.max(0, ...grid.flat().map(slot => slot.count));
```
(Guard against an all-zero grid so `Math.max` doesn't receive an empty spread; `Math.max(0, ...)` handles that.) If the intent really is "relative to all-time data" rather than "relative to what's rendered," update the header/`bucketFor` comments to say so explicitly instead of promising a guarantee the current window-truncation logic doesn't deliver.

### WR-02: `currentStreak` semantics can mislead — it is not "current" relative to today, only relative to the last *active* day

**File:** `src/commands/heatmap.js:91-107` (`computeSummaryStats`), rendered at `heatmap.js:297` (`renderSummary`).

**Issue:** `currentStreak` is documented as "the run ending on `lastDay`," where `lastDay` is simply the most recent day present in `dayMap` — not necessarily today. If a user has not recorded any turns in the last week, `computeSummaryStats` will still report a nonzero "Current streak" reflecting a streak that ended a week ago, with no indication in the rendered summary (`renderSummary`, `heatmap.js:287-300`) that the streak is stale/broken. A reader of the CLI output reasonably expects "Current streak" to mean "streak that is still active as of now," similar to how GitHub/Duolingo-style streak counters work (i.e., 0 if you missed today or yesterday). No test in `heatmap.test.js` exercises this boundary (the D-04 fixture test at lines 96-111 never asserts `currentStreak`, and the only place it's asserted is the empty-map case, `heatmap.test.js:113-124`).

**Fix:** Either (a) rename the field to something unambiguous like `lastStreak` / `streakEndingLastActiveDay`, or (b) pass "today" into `computeSummaryStats` and zero out `currentStreak` when `lastDay` isn't today or yesterday. Whichever is chosen, add a test asserting the behavior when the last active day is in the past relative to "now."

### WR-03: `run()` has no top-level error handling around `blameUtil.listAllTurns`/cache access, unlike sibling commands

**File:** `src/commands/heatmap.js:307-346` (`run`).

**Issue:** `blame.js`, `cost.js`, `gc.js`, and `log.js` all wrap fallible operations (JSON parsing, network calls, cache access) in `try/catch` and print a user-facing error via `console.error` before `process.exit(1)`. `heatmap.js:run()` calls `blameUtil.listAllTurns({ noCache })` with no surrounding try/catch. In the normal path this is safe today because `listAllTurns` itself catches cache errors and `gitSafe` never throws — but this is an implicit invariant across two other files (`blame-util.js:60-71`, `git.js:30-36`) that `heatmap.js` silently depends on rather than defending against locally. If either of those invariants changes in a future edit (e.g. a cache migration bug that throws instead of returning `[]`), `heatmap.js` will produce a raw uncaught stack trace instead of the friendly error message pattern used elsewhere in the codebase.

**Fix:** Not strictly required given current invariants, but for consistency with the rest of the command surface, consider wrapping the enumeration call:
```javascript
let turns;
try {
  turns = blameUtil.listAllTurns({ noCache });
} catch (e) {
  console.error(`git turn: failed to enumerate turns: ${e.message}`);
  process.exit(1);
}
```

## Info

### IN-01: Redundant ISO round-trip to compute `endDate`

**File:** `src/commands/heatmap.js:317`

**Issue:** `const endDate = dayKey(new Date().toISOString());` constructs a `Date`, serializes it to an ISO string, then immediately re-parses that string back into a `Date` inside `dayKey` purely to read local date components. The `toISOString()`/re-parse round-trip is unnecessary — `dayKey` only needs any value `new Date()` can accept.

**Fix:**
```javascript
const endDate = dayKey(new Date());
```
(`dayKey` already does `new Date(isoTs)`, and `new Date(Date)` is a no-op copy, so this is equivalent and skips the string round-trip.)

### IN-02: `renderMonthLabels` relies on an unstated invariant (only the chronologically-first slot per column is checked)

**File:** `src/commands/heatmap.js:232-257`

**Issue:** The function iterates each column's slots and only inspects the **first** non-null slot (`break` at line 252) rather than checking all 7 days in the column for a day-of-month in `1..7`. This happens to be correct today because (a) columns are populated in chronological order Sun→Sat, (b) null padding only ever occurs at the *end* of the final column (future days), never at the start, and (c) exactly one Sunday per month falls within days 1-7. That chain of reasoning is not stated anywhere near the `break` — the adjacent comment ("one date-check per column is enough to detect month transitions") asserts the conclusion without explaining why checking only the first slot is sufficient. A future maintainer changing the null-padding rules (e.g. adding null padding to the *start* of the first column for partial weeks) would silently break month-label placement without any test catching the specific failure mode, since `heatmap.test.js:325-340` only asserts spacing between labels, not that every month change is actually labeled.

**Fix:** Either add an explicit comment tying the shortcut to the specific invariants it depends on (chronological ordering + end-only null padding), or make the loop robust by scanning all `column` slots for a day-of-month in `1..7` instead of relying on slot ordering:
```javascript
for (const slot of column) {
  if (!slot.date) continue;
  const [, mStr, dStr] = slot.date.split('-');
  const monthIdx = parseInt(mStr, 10) - 1;
  const dayOfMonth = parseInt(dStr, 10);
  if (dayOfMonth >= 1 && dayOfMonth <= 7 && monthIdx !== lastLabeledMonth) {
    // ... place label ...
    lastLabeledMonth = monthIdx;
    break;
  }
}
```

### IN-03: Magic numbers `3`/`7`/`4` in `renderMonthLabels`/`buildWeekColumns` lack named constants

**File:** `src/commands/heatmap.js:158` (`(weeks - 1) * 7`), `heatmap.js:245` (`col - lastLabelCol > 3`), `heatmap.js:244` (`dayOfMonth >= 1 && dayOfMonth <= 7`)

**Issue:** `7` (days per week) and `3` (minimum column gap between month labels, chosen because `MONTH_ABBREVS` entries are 3 characters wide) are repeated as bare literals without names, unlike `LABEL_WIDTH`/`CELL_WIDTH`/`MAX_WEEKS`, which are already named constants at the top of the file (lines 122-124). This is a minor readability nit — the values are small and locally obvious — but it's inconsistent with the file's own established convention of naming its layout constants.

**Fix:**
```javascript
const DAYS_PER_WEEK = 7;
const MONTH_LABEL_MIN_GAP_COLS = 3; // MONTH_ABBREVS entries are 3 chars wide
```
and reference these instead of the bare literals at the sites above.
