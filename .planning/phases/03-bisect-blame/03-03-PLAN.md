<objective>
Implement `git turn bisect <cmd>`: binary-search the cross-session turn snapshots, run `<cmd>` against each candidate, and report the first turn where `<cmd>` fails — then always put the worktree back exactly as it was.

Purpose: roadmap success criterion 2 for Phase 3 and locked decisions D-03 (clean-worktree precondition), D-04 (snapshot before starting, guaranteed restore on every exit path) and D-05 (live progress commentary plus a final verdict).

The structural template is `src/commands/revert.js`: snapshot the current state first, then restore. Bisect extends it with a loop over many candidate restores, so the single guaranteed restore moves into a `finally`, plus signal handlers, because `spawnSync` is blocking and a Ctrl-C during the child's run must not leave a candidate tree checked out over the user's work.

Output: `src/commands/bisect.js`, `src/commands/bisect.test.js`.
</objective>

## Module exports (deliberate deviation from the `{ run }`-only convention)

`module.exports = { run, bisectCore };`

Every other command in `src/commands/` exports only `run`. Bisect additionally exports `bisectCore` because its failure paths are the behaviour under test and `process.exit` is not assertable — no existing test in this repo exercises a `process.exit` path. `run` stays the thin CLI wrapper; `bisectCore` throws instead of exiting and accepts injected collaborators.

### `bisectCore(options)` -> result object

Options:
- `cmd` (string, required) — the shell command to test each candidate with
- `noCache` (boolean, default false) — forwarded to `listAllTurns`
- `runCommand` (function, default the real `spawnSync` runner) — called as `runCommand(cmd, cwd)` and must return `{ status }` where `status` is a number or null; injected by tests to drive exit codes deterministically
- `log` (function, default `console.log`) — progress sink

Returns one of:
- `{ result: 'found', turn }` — `turn` is the first candidate where `<cmd>` failed
- `{ result: 'clean', tested }` — no candidate failed
- `{ result: 'all-skipped', tested }` — every tested candidate exited 125
- `{ result: 'aborted', code }` — a candidate exited >= 128 or was killed (status null)

Throws `Error` with these messages (no `git turn: ` prefix — `run` adds it):
- `bisect requires a clean worktree. Commit or stash changes first.` (D-03)
- `no turn snapshots reachable from HEAD to bisect`

### `run(args)`

- `readSession()` null -> `console.error('git turn: not initialized. Run \`git turn init\` first.')`, exit 1 (matching revert.js lines 7-11)
- `cmd` is every argument that does not start with `--`, joined with a single space, so both `git turn bisect "npm test"` and `git turn bisect npm test` work
- empty `cmd` -> `console.error('Usage: git turn bisect <cmd>')`, exit 1
- `--no-cache` recognised, same meaning as on `log` and `blame`
- catches errors thrown by `bisectCore`, prints `` `git turn: ${err.message}` `` and exits 1
- exits 1 when the result is `aborted`, 0 otherwise

## Exact output strings (D-05 — the tests assert on these)

| Moment | Line |
|--------|------|
| Start | `` `Bisecting ${candidates.length} turns with: ${cmd}` `` |
| Per candidate, before running | `` `  turn ${String(turn.turn_n).padStart(2)}  ${(turn.head_sha \|\| turn.snapshot_sha).slice(0, 7)}  testing...` `` |
| Verdict, exit 0 | `  PASS` |
| Verdict, other nonzero < 128 | `  FAIL` |
| Verdict, exit 125 | `  SKIP (untestable, exit 125)` |
| Result `found` | `` `turn ${turn.turn_n} introduced the failure (${(turn.head_sha \|\| turn.snapshot_sha).slice(0, 7)})` `` |
| Result `clean` | `` `No failing turn found in ${tested} candidates` `` |
| Result `all-skipped` | `` `All tested candidates were untestable (exit 125)` `` |
| Result `aborted` | `` `Bisect aborted: command exited ${code}` `` |
| Always last | `Restored pre-bisect state` |

## Exit-code classification (git bisect run convention, 03-RESEARCH.md Pattern 4)

| `status` | Meaning |
|----------|---------|
| `0` | good |
| `125` | untestable — skip this candidate |
| `null` or `>= 128` | abort the whole search (killed by signal / fatal) |
| anything else nonzero | bad |

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CLI argv (`<cmd>`) -> system shell | The user's own command string is executed verbatim through `/bin/sh`. This boundary is the feature |
| git refs (`refs/git-turn/sessions/*`) -> worktree | Candidate snapshot trees are checked out over the user's working files during the search |
| Process signals -> worktree state | An interrupt mid-search can leave a candidate tree in place |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-21 | Tampering / Elevation of Privilege | `spawnSync(cmd, { shell: true })` in `defaultRunCommand` | accept | `<cmd>` is by definition an arbitrary shell command the invoking user supplies, exactly as `git bisect run <cmd>` does. It is not attacker-controlled input: the only party who can set it is the person typing at the shell, who already has full shell privileges on the machine. There is no privilege boundary to cross and therefore no injection to prevent — refusing shell mode would only break documented UX (`git turn bisect "npm test -- --grep foo"`). The project's "never use shell string interpolation" rule targets constructing *git* argv from data, which this file continues to honour: every git call in `bisect.js` goes through `gitSafe` with an argv array. Mitigation is documentation only: plan 03-04 states in README.md and AGENTS.md that `<cmd>` runs with the user's own shell privileges. Enforced by the acceptance criterion that `shell: true` appears exactly once in the file |
| T-03-22 | Tampering | `restoreSnapshot` on a candidate whose `head_sha` is unreachable | mitigate | Candidates are filtered through `isAncestor(turn.head_sha, 'HEAD')` before entering the search, so a turn belonging to a force-pushed, rebased or deleted branch is never checked out over the user's files. `restoreSnapshot`'s existing branch-mismatch guard is a second line of defence |
| T-03-23 | Tampering (destructive) | candidate checkout overwriting uncommitted work | mitigate | Three layers: the D-03 clean-worktree gate refuses to start when anything is uncommitted; the D-04 pre-bisect `snapshotWorktree()` captures recoverable state including untracked files before any mutation; the `finally` plus SIGINT/SIGTERM handlers restore that state on every exit path. Residual gap explicitly accepted and documented: SIGKILL or a detached/reparented child can still escape, in which case the stderr recovery hint names the exact `git read-tree --reset -u <sha>^{tree}` command |
| T-03-24 | Repudiation | no record of a bisect that moved the worktree | mitigate | `bisect-start` records `cmd` and `pre_bisect_snapshot_sha` before the search; `bisect-end` records the outcome. Both land in `.git/git-turn/ops/` via `writeOp`, so a bisect that ended badly is auditable and its pre-state sha is recoverable |
| T-03-25 | Denial of Service | very long turn history inflating search cost | accept | The search is O(log n) candidate checkouts, so even thousands of turns cost only a handful of `read-tree` operations — the dominant cost is `<cmd>` itself, which the user chose. Candidate *enumeration* is O(n) and shares the accepted rationale from plan 03-01: turn count is local, single-user data that no third party can inflate, and it is bounded by `gc --keep-sessions`. This is a performance characteristic, not a security exposure, and is called out here explicitly so it is not re-raised as a vulnerability |
| T-03-26 | Information Disclosure | `<cmd>` output streamed to the terminal via `stdio: 'inherit'` | accept | Output goes to the user's own TTY and is never parsed as structured data or persisted — bisect branches only on `result.status`, never on stdout/stderr content, so there is no path for `<cmd>` output to inject values into the op log or the SQLite cache |
| T-03-SC | Tampering | package installs | mitigate | No packages installed; `package.json` gains no `dependencies` block. Legitimacy gate not applicable per 03-RESEARCH.md |
