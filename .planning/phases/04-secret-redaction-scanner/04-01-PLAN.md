<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller (Phase 5 `record-prompt`, agent-supplied prompt/response text) → `redact(text)` | Fully untrusted, arbitrary-length, arbitrary-content free text crosses into the scanner. The scanner treats it as data only — it is never eval'd, never compiled into a regex, and never used to construct a pattern. |
| `redact()` output → note-write path (Phase 5) → `refs/notes/git-turn` | Everything past this boundary is permanent and unreachable by `git filter-repo`/BFG. Anything not redacted here is effectively unremovable, which is why the scanner has no opt-out. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-01 | Denial of Service | `SECRET_PATTERNS` regex evaluation in `redact()` (`src/redact.js`) | mitigate | Every pattern uses bounded quantifiers (`{16}`, `{36}`, `{82}`, `{58,74}`, `{93}`, generic value capture capped at `{12,150}`) or non-nested simple character classes — no nested quantifiers, no overlapping alternation. Task 2 forbids relaxing any bound; Task 3 adds an automated ReDoS regression test (300 KB adversarial blob must complete under 2000 ms). |
| T-04-02 | Tampering / Information Disclosure | Encoding-based redaction bypass — a secret base64/URL-encoded before being pasted matches no vendor pattern | accept | Out of scope for REDACT-01 per 04-RESEARCH.md Security Domain: multi-encoding-aware scanning is a materially larger feature. Documented, not silent — Task 3 adds a `KNOWN LIMITATIONS` paragraph to the module comment and an explicit test asserting the gap so it is tracked rather than assumed absent. |
| T-04-03 | Information Disclosure | Redaction marker leaking secret structure or content (`[REDACTED-AWS-KEY]`, `sk-...ab12` partial reveal, per-type counts) | mitigate | D-01 enforced: single untagged literal `[REDACTED]` for every match; `redact()` returns only a total `count` with no type, position, or content breakdown; `module.exports` is exactly `{ redact }` so no importer can enumerate `SECRET_PATTERNS`. Task 1 asserts no `[REDACTED-`/`[REDACTED:` form appears; Task 2 acceptance greps for it. |
| T-04-04 | Tampering | Bypassing the scanner at the call site via an option, flag, or env var | mitigate | `redact(text)` takes exactly one parameter; no options object, no env-var read. Task 3 asserts `redact.length === 1` and that a trailing `{ enabled: false }` argument still yields `count` 1. |
| T-04-05 | Information Disclosure | Multi-line PEM private key surviving because the scanner processed input per line | mitigate | `redact()` never splits on `\n`; the whole string is scanned in one pass. The multi-line PEM fixture in Task 1 proves the header pattern fires across a full multi-line block. Module comment states the calling convention: scan before `JSON.stringify`, never on escaped text. |
| T-04-06 | Spoofing / Availability (correctness) | Legitimate 40-hex commit SHAs and UUID-v4 session ids destroyed by false-positive entropy redaction, corrupting diagnostic content | mitigate | D-03 whitelist runs against the raw candidate token before any entropy math (empirically necessary: a real SHA scores 3.83 bits/char, above the 3.0 hex threshold). | T-04-SC | Tampering | Supply chain via package installs | not applicable | No `npm`/`pip`/`cargo` install occurs in this phase. 04-RESEARCH.md § Package Legitimacy Audit records this as genuinely inapplicable (zero-dependency constraint), not skipped.
